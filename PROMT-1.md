Ты работаешь над существующим проектом **KingPromotion**.

Мне необходимо провести полноценный аудит и рефакторинг системы авторизации.

ВАЖНО: сначала внимательно изучи существующую архитектуру проекта, backend, frontend, модели БД, существующие endpoints, сервисы, repositories, JWT/session-механику, Telegram/VK OAuth и только после этого вноси изменения.

Не создавай параллельную систему авторизации, если необходимые механизмы уже существуют. Максимально используй текущую архитектуру проекта, но исправляй её там, где существующая реализация мешает требованиям ниже.

# 1. Основная задача

В системе должно существовать **три независимых способа регистрации/авторизации**:

1. Логин/почта + пароль.
2. Telegram.
3. VK.

Telegram и VK должны работать как полноценная **passwordless authentication**.

Пользователь, который зарегистрировался через Telegram или VK, НЕ должен:

* придумывать логин;
* придумывать пароль;
* вводить пароль после OAuth;
* проходить дополнительную форму регистрации;
* создавать локальные credentials только ради использования сайта.

Если Telegram/VK успешно подтвердил личность пользователя — этого достаточно для создания аккаунта и входа.

# 3. Требуемая модель авторизации

Система должна логически разделять:

## LOCAL AUTH

Пользователь самостоятельно регистрирует аккаунт через:

* login;
* email, если email является частью существующей модели;
* password.

После регистрации он может входить через:

* login + password;

и, если существующая система это поддерживает:

* email + password.

---

## TELEGRAM AUTH

Пользователь проходит Telegram authorization.

После успешной проверки Telegram:

### Если Telegram-пользователь уже существует:

Найти существующий аккаунт по постоянному Telegram ID.

Авторизовать пользователя.

Создать обычную авторизованную сессию/JWT точно такого же уровня, как при обычном входе.

Перенаправить пользователя в приложение.

Никакого пароля не спрашивать.

### Если Telegram-пользователя ещё нет:

Автоматически создать пользователя в основной таблице пользователей.

Создать/сохранить связь пользователя с Telegram account.

Сохранить необходимые данные Telegram.

Минимально:

* telegram_user_id;
* username, если присутствует;
* first_name, если присутствует;
* last_name, если присутствует;
* avatar/photo, если архитектура проекта это предусматривает.

Но главным идентификатором должен быть именно:

`telegram_user_id`

а НЕ Telegram username.

Username пользователь может изменить, Telegram ID — постоянный.

После создания пользователя:

* сразу авторизовать его;
* создать JWT/session;
* НЕ отправлять на форму создания пароля;
* НЕ просить придумать логин;
* НЕ требовать email.

После этого пользователь должен считаться полноценным зарегистрированным пользователем KingPromotion.

# 4. Сообщение Telegram после первой регистрации

Если пользователь был создан впервые именно через Telegram, Telegram-бот должен отправить ему приветственное сообщение.

Например:

«Вы успешно зарегистрировали аккаунт в KingPromotion.

Спасибо, что пользуетесь KingPromotion!»

Можешь немного улучшить формулировку, но сообщение должно быть коротким.

ВАЖНО:

Сообщение должно отправляться только после первой успешной регистрации через Telegram.

При каждом последующем входе отправлять его НЕ нужно.

Ошибка отправки Telegram-сообщения НЕ должна отменять регистрацию пользователя.

То есть:

создание пользователя → успешно;

JWT → успешно;

отправка Telegram сообщения → дополнительное действие.

Если Telegram API/бот временно недоступен, пользователь всё равно должен успешно зарегистрироваться и войти.

Ошибку нужно корректно залогировать.

# 5. VK AUTH

VK должен работать абсолютно по тому же принципу.

После успешной OAuth-авторизации VK:

### Если VK account уже связан с пользователем:

найти пользователя по постоянному `vk_user_id`;

создать JWT/session;

авторизовать;

перенаправить в приложение.

### Если VK account ещё не существует:

автоматически создать пользователя;

создать связь с VK;

сохранить необходимые данные;

сразу авторизовать;

создать JWT/session;

НЕ требовать:

* логин;
* пароль;
* дополнительную форму регистрации;
* подтверждение создания аккаунта.

Основной social identifier:

`vk_user_id`.

Нельзя полагаться на имя, username, display name или URL страницы как на уникальный идентификатор.

# 6. Очень важное правило модели User

Не делай `password` обязательным для всех пользователей.

У social-only пользователя пароль может отсутствовать.

Например:

`password_hash = NULL`

если это соответствует архитектуре проекта.

Аналогично нельзя искусственно записывать:

* случайный пароль;
* `"telegram"`;
* `"vk"`;
* пустую строку;
* фиктивный hash.

Это плохая архитектура.

Наличие или отсутствие пароля должно отражать реальное состояние аккаунта.

# 7. Не создавай фиктивные логины

Если существующая таблица `users` сейчас требует обязательный уникальный `login`, сначала изучи, где и зачем он используется.

Не создавай пользователям значения типа:

`telegram_123456`
`vk_123456`
`user_123456`

только для обхода ограничения БД, если в этом нет реальной продуктовой необходимости.

Предпочтительная архитектура:

* внутренний `users.id` — главный идентификатор пользователя;
* login может быть nullable для social-only аккаунта;
* email может быть nullable;
* password_hash может быть nullable.

Социальные аккаунты связываются через отдельную таблицу вроде:

`user_social_accounts`

если она уже существует.

Не создавай новую таблицу, если существующая `user_social_accounts` уже выполняет эту роль — адаптируй её.

# 8. Предпочтительная структура social accounts

Если в проекте уже существует таблица вроде:

`user_social_accounts`

используй её.

Пример логической структуры:

* id
* user_id
* provider
* provider_user_id
* username
* display_name
* avatar_url
* created_at
* updated_at

Где:

`provider = telegram | vk`

Уникальность должна быть как минимум:

`UNIQUE(provider, provider_user_id)`

Это должно гарантировать, что один Telegram/VK account не создаст несколько пользователей из-за race condition.

Проверь существующие constraints и индексы.

# 10. Форма регистрации

На странице регистрации должна быть форма создания LOCAL-аккаунта.

Основные поля:

### Логин

Соблюдай существующие ограничения проекта.

Если уже есть backend/frontend validation — не дублируй её бессистемно, а приведи к единой логике.

### Email

Если email уже является обязательной частью локальной регистрации — оставить.

Если по архитектуре он необязательный — не делай его обязательным самовольно.

### Пароль

Создание password hash выполняется только на backend.

Frontend никогда не хеширует пароль самостоятельно.

Если уже существуют требования сложности пароля — сохранить их.

### Подтверждение пароля

Если UI проекта подразумевает это поле, добавить:

`passwordConfirmation`

Но подтверждение пароля является frontend validation и не должно храниться в БД.

# 12. Один пользователь — несколько методов входа

Очень внимательно изучи существующую реализацию `user_social_accounts`.

Архитектура должна позволять одному `users.id` иметь несколько способов авторизации.

Например один пользователь потенциально может иметь:

* local credentials;
* Telegram;
* VK.

Но НЕ объединяй аккаунты автоматически только на основании одинакового имени.

И особенно НЕ объединяй автоматически:

Telegram username == login

или

VK name == login.

Это небезопасно.

Если account linking уже существует — сохрани правильную логику.

Если не существует — сейчас не внедряй сложную систему объединения аккаунтов без необходимости.

# 13. JWT/session

После любого из трёх видов авторизации:

* local;
* Telegram;
* VK;

результат должен быть одинаковым.

То есть frontend после успешной авторизации не должен знать, каким способом пользователь вошёл, кроме случая, когда эта информация нужна интерфейсу.

Все три метода должны приводить к одной общей функции вроде:

`create_access_token(user_id)`

или существующему аналогу.

Не создавай три разных JWT-механизма.

JWT должен идентифицировать внутренний:

`users.id`

а НЕ Telegram/VK ID.

Например `sub = users.id`.

# 14. Security

Обязательно проверь безопасность существующих social auth flows.

Для Telegram:

проверь, что данные авторизации действительно валидируются сервером согласно используемому Telegram authentication flow.

Нельзя доверять данным типа:

`telegram_id`

которые frontend самостоятельно прислал на backend без криптографической проверки.

Для VK:

проверь OAuth callback;

проверку `state`;

обмен authorization code на token;

получение VK user ID от VK;

redirect URI;

защиту от подмены callback.

Нельзя принимать от frontend просто:

`vk_user_id`

и считать пользователя авторизованным.

---

# 15. Race conditions

Обработай ситуацию, когда одновременно приходят два запроса регистрации одного social account.

Например два callback Telegram/VK одновременно.

База данных должна гарантировать уникальность social account.

Алгоритм должен корректно переживать `IntegrityError`.

Не должно появляться:

два пользователя для одного Telegram ID

или

два пользователя для одного VK ID.

---

# 16. Транзакции

Создание нового social пользователя должно быть атомарным.

Пример:

1. создаём User;
2. создаём SocialAccount;
3. commit.

Если создание SocialAccount завершилось ошибкой — не должен оставаться "пустой" пользователь без корректной связи, если только существующая архитектура специально этого не допускает.

Используй транзакцию.

# 17. Что делать со старым flow Telegram + password

Полностью найди существующий flow:

Telegram auth
→ обнаружение нового пользователя
→ запрос создать password
→ сохранение password
→ завершение регистрации.

Его необходимо удалить.

После Telegram verification flow должен быть:

Telegram verification
→ поиск social account
→ существующий user ИЛИ создание нового user
→ JWT/session
→ приложение.

Аналогично VK.

Удаляй также ненужные:

* endpoints;
* schemas;
* frontend states;
* компоненты;
* temporary tokens;
* pending registration state;

НО только если подтвердил, что больше ничего в проекте ими не пользуется.

Не оставляй мёртвый код.

# 20. Желательная общая функция social login

Если архитектура позволяет, Telegram и VK должны использовать общий service-level механизм.

Например концептуально:

`authenticate_social_user(provider, provider_user_id, profile_data)`

Логика:

1. найти SocialAccount;
2. если найден:

   * получить User;
3. если не найден:

   * создать User;
   * создать SocialAccount;
   * определить `is_new_user = True`;
4. создать access token;
5. вернуть результат.

Provider-specific code должен заниматься только получением и проверкой личности.

Например:

Telegram adapter:
Telegram → verified Telegram identity.

VK adapter:
VK OAuth → verified VK identity.

После этого используется одна общая бизнес-логика.

Но не внедряй именно такую функцию механически, если существующая архитектура проекта уже решает задачу лучше.

# 21. Frontend auth state

Ожидаемые состояния:

* unauthenticated;

Дополнительные состояния OAuth типа loading/error допустимы.

`TelegramUser`
`VKUser`
`PasswordUser`.

`User`.

# 28. Password

Проверь текущий password hashing.

Новые пароли нельзя хранить в plaintext.

Если проект до сих пор использует устаревший MD5 из legacy-системы, не начинай автоматически менять все существующие пароли без анализа совместимости.

Для новых password credentials желательно использовать современный password hashing механизм проекта, например Argon2/bcrypt/passlib, если это можно безопасно внедрить.

Если legacy password compatibility необходима — сохрани её отдельно и объясни решение.

Telegram/VK вообще не должны иметь password hash, пока пользователь самостоятельно не создаст password credentials в будущем.

# 31. После OAuth redirect

Особенно внимательно проверь текущий redirect после Telegram/VK.

После успешной social authorization пользователь должен:

1. получить авторизованную session/JWT;
2. попасть в приложение;
3. при refresh оставаться авторизованным согласно существующему TTL;
4. `/check-token` или `/auth/me` должны корректно его определить.

Не используй URL query parameters для передачи долгоживущего access token, если архитектура позволяет использовать более безопасный механизм.

Если существующая система передаёт JWT через URL — оцени риск и по возможности исправь, не ломая flow.

# Конечный ожидаемый UX

Пользователь открывает страницу входа KingPromotion.

Он видит:

**Логин или почта**
**Пароль**
**Войти**

**Войти через Telegram**

**Войти через VK**

**Регистрация**

---

Если выбирает Telegram:

Telegram → подтверждение → сразу внутри KingPromotion.

При первом входе автоматически создаётся пользователь.

Telegram-бот отправляет:

«Вы успешно зарегистрировали аккаунт в KingPromotion. Спасибо, что пользуетесь KingPromotion!»

Никаких паролей.

---

Если выбирает VK:

VK → подтверждение → сразу внутри KingPromotion.

При первом входе автоматически создаётся пользователь.

Никаких паролей.

---

Если нажимает «Регистрация»:

открывается отдельная страница `/register`.

Там пользователь самостоятельно создаёт обычный аккаунт через login/password и остальные необходимые поля существующей local registration.

Главное архитектурное правило:

**Telegram и VK подтверждают личность пользователя сами, поэтому пароль KingPromotion для этих способов входа не требуется. Пароль существует только как credential для локальной авторизации.**
