## Рабочая директория

Frontend:

`/home/ava/king/frontend`

Backend находится в существующем проекте KingPromotion. Перед изменениями самостоятельно найди его расположение и изучи текущую архитектуру.

Под intro-блоком создать компактную статистику отзывов.

Пример:

Статистика должна быть компактной.

Не превращать её в огромную dashboard-панель.

Если backend отзывов реализуется сейчас — статистика должна вычисляться из реальных данных.

Если по объективной причине backend статистики пока использовать невозможно, frontend-структура должна позволять заменить источник данных без изменения UI-компонентов.

# 8. Карточка отзыва

Каждый отзыв должен содержать:

* аватар;
* username/login;
* дату публикации;
* rating от 1 до 5;
* визуальные звёзды;
* текст.

Пример:

Аватар

username

★★★★★

12 сентября 2026

Пользуюсь сервисом уже несколько месяцев...

Карточки сделать компактными.

Не создавать огромные панели с большим количеством пустого пространства.

Аватар и username по возможности получать через связь Review → User.

Не дублировать пользовательские данные в Review без необходимости.

Если у пользователя нет аватара — использовать уже существующий fallback проекта либо аккуратный fallback на основе username.

На mobile:

Предпочтительно использовать pagination/cursor механизм, который уже принят в backend проекта.

Не изобретать новый стандарт, если backend уже имеет pagination.

После загрузки новой страницы не дублировать существующие отзывы.

# 12. Авторизация

При нажатии:

**Оставить отзыв**

проверить пользователя через существующую систему авторизации KingPromotion.

Критически важно:

**не создавать второй AuthContext, отдельную проверку токена или параллельную auth-систему.**

Использовать текущий источник состояния пользователя.

## Авторизованный пользователь

Открыть форму создания отзыва.

## Неавторизованный пользователь

Показать modal/уведомление:

**Чтобы оставить отзыв, необходимо войти в аккаунт.**

Кнопки:

**Войти**

**Отмена**

`Войти` должен запускать существующий auth flow.

Если проект поддерживает `returnUrl`, `redirectTo`, location state или аналогичный механизм — использовать его.

Желательное поведение:

`/reviews → login → успешная авторизация → /reviews`

Не ломать существующий auth flow ради этой функции.

# 14. Валидация

Нельзя отправлять отзыв:

* без rating;
* с пустым текстом;
* с текстом меньше 10 символов;
* с текстом больше 1000 символов.

Перед проверкой текста учитывать trim, чтобы строка из пробелов не считалась отзывом.

Ошибки показывать непосредственно около соответствующего поля.

Не использовать:

* `alert()`;
* `confirm()`;
* стандартные браузерные popup.

Сохранять существующий стиль ошибок форм KingPromotion.

После отправки формы:

* перевести кнопку в loading;

* сделать кнопку disabled;
* предотвратить повторную отправку;

После успешной публикации:

* закрыть modal;
* очистить локальное состояние формы;
* обновить отзывы;
* обновить статистику;
* показать существующее success-уведомление проекта.

Если отзыв публикуется сразу:

**Спасибо! Ваш отзыв опубликован.**

Если существующая архитектура предполагает moderation:

**Спасибо! Отзыв отправлен на модерацию.**

Не придумывай модерацию самостоятельно. Сначала изучи backend.

# 17. Один отзыв на пользователя

Предпочтительная бизнес-логика:

**один активный отзыв на одного пользователя.**

Ограничение должно обеспечиваться backend, а не только frontend.

Если пользователь уже оставил отзыв:

* frontend должен корректно это показать;
* вместо создания второго отзыва желательно предоставить `Редактировать отзыв`.

Если полноценное редактирование естественно вписывается в текущую архитектуру — реализуй его.

Если это значительно расширяет scope, как минимум спроектируй backend так, чтобы нельзя было создавать десятки отзывов одним пользователем и последующее добавление PATCH/PUT не потребовало переработки модели.

По возможности обеспечить уникальность на уровне БД, а не только проверкой вида:

`SELECT → если нет → INSERT`

чтобы избежать race condition при двух одновременных запросах.

# 18. API

Если API отзывов отсутствует, реализуй endpoints согласно существующему стандарту проекта.

Логически потребуются операции:

```text
GET reviews
POST review
GET review statistics
```

При реализации редактирования:

```text
PATCH/PUT review
```

Однако названия URL и структура должны соответствовать текущей архитектуре KingPromotion.

Не копировать `/reviews` вслепую, если backend использует другой API prefix или naming convention.

GET должен поддерживать:

* pagination;
* sorting.

POST должен требовать авторизацию.

# 19. Безопасность

Frontend-проверка авторизации является только UX-механизмом.

Она НЕ является защитой API.

Backend обязан самостоятельно проверять пользователя.

При POST Review:

**никогда не доверять `user_id`, переданному frontend.**

Frontend вообще не должен определять автора отзыва через произвольный `user_id`.

Backend получает текущего пользователя через существующую систему:

* JWT;
* session;
* dependency;
* middleware;

в зависимости от архитектуры проекта.

Неавторизованный POST должен возвращать корректный статус, например:

`401 Unauthorized`

Также backend обязан самостоятельно валидировать:

* rating;
* text;
* минимальную длину;
* максимальную длину;
* ограничения количества отзывов.

Нельзя полагаться только на frontend validation.

* мягкое изменение border;
* подсветка rating;
* открытие/закрытие modal;
* transition кнопок;

Не использовать:

* сильный scale;
* прыжки;
* постоянные движения;

# Главный приоритет

Итоговый пользовательский сценарий:

`/reviews`

→ пользователь видит реальные отзывы

→ видит общий рейтинг

→ может изменить сортировку

→ может загрузить дополнительные отзывы

→ нажимает `Оставить отзыв`

→ система проверяет существующую авторизацию

→ авторизованный пользователь выбирает оценку

→ пишет отзыв

→ отправляет его

→ backend самостоятельно определяет автора

→ отзыв сохраняется

→ пользователь получает понятный результат

→ список и статистика обновляются.

Главные приоритеты разработки:

**единый дизайн KingPromotion → качественный UX → корректная интеграция с существующей архитектурой → безопасность backend → чистый код → адаптивность → отсутствие дублирования → отсутствие регрессий.**

Не ограничивайся визуальным макетом. Задача считается выполненной только тогда, когда страница интегрирована в существующий проект, взаимодействует с реальной авторизацией и backend, а основные сценарии проверены.
