# Задача: внедрение FreeKassa, Heleket и CrystalPay в существующую платежную систему

Работаем с существующим проектом.

Необходимо полноценно интегрировать три новых платежных провайдера:

* FreeKassa
* Heleket
* CrystalPay

ВАЖНО: в проекте уже существует платежная логика и интеграция YooKassa.

Нельзя просто написать три отдельных обработчика рядом с существующей системой.

Задача — сначала изучить текущую архитектуру проекта, существующую БД, модели заказов, текущую YooKassa-интеграцию и frontend оформления заказа, а затем аккуратно расширить существующую систему.

# 3. АРХИТЕКТУРА ПЛАТЕЖЕЙ

Нужно привести платежи к единой архитектуре.

Желательный принцип:

```text
PaymentService
        |
        + YooKassa
        |
        + FreeKassa
        |
        + Heleket
        |
        + CrystalPay
```

Каждый провайдер должен реализовывать одинаковый внешний контракт.

Например:

```python
class PaymentProvider:
    async def create_payment(...):
        ...

    async def get_payment_status(...):
        ...

    async def handle_webhook(...):
        ...
```

Можно использовать Protocol / ABC / обычный интерфейс — выбери решение, соответствующее стилю существующего проекта.

Не делай лишнюю абстракцию ради абстракции.

Но бизнес-логика заказа не должна знать детали API FreeKassa, Heleket или CrystalPay.

# 6. НИКОГДА НЕ ДОВЕРЯТЬ СУММЕ С FRONTEND

Frontend НЕ должен определять сумму платежа.

Запрещён такой подход:

```json
{
    "order_id": 1251,
    "amount": 100
}
```

с дальнейшей отправкой этих 100 рублей провайдеру.

Frontend отправляет только идентификатор заказа и выбранного провайдера.

Backend самостоятельно получает заказ:

```python
order = await order_repository.get_by_id(order_id)
```

и берёт реальную сумму:

```python
amount = order.total_price
```

или аналогичное существующее поле.

Если пользователь попытается создать платеж для чужого заказа — отказ.

Если заказ уже оплачен — новый платеж без необходимости не создаём.

Если заказ отменён или находится в состоянии, в котором оплата запрещена — отказ.

# 9. FREEKASSA

Изучи АКТУАЛЬНУЮ официальную документацию FreeKassa перед реализацией.

Не опирайся только на память или старые статьи.

FreeKassa поддерживает как SCI, так и API.

Нужно выбрать оптимальный вариант для нашего UX.

Если пользователь выбирает просто:

```text
FreeKassa
```

и после этого должен попасть на страницу FreeKassa и самостоятельно выбрать доступный способ оплаты — предпочтительно использовать hosted payment flow / SCI.

Не хардкодить конкретный `i` payment method без необходимости.

Если существующий интерфейс подразумевает выбор конкретного способа внутри FreeKassa, можно использовать API создания заказа через актуальный `/v1/orders/create`.

В любом случае интеграция должна:

* сформировать корректный платеж;
* использовать реальный `order_id`;
* использовать сумму из БД;
* сформировать подпись строго по актуальной документации;
* сохранить provider payment ID, если он предоставляется;
* вернуть payment URL frontend.

### Webhook FreeKassa

Создать отдельный endpoint вида:

```text
/api/payments/webhooks/freekassa
```

или привести к существующему стилю роутинга.

При callback:

1. Получить данные уведомления.
2. Проверить обязательные поля.
3. Найти наш платеж/заказ.
4. Проверить подпись по актуальной документации FreeKassa.
5. Использовать Secret Word 2 там, где этого требует webhook-схема.
6. Использовать constant-time сравнение подписи, где применимо.
7. Проверить merchant.
8. Проверить order ID.
9. Проверить сумму.
10. Проверить валюту, если она приходит и используется.
11. Проверить текущее состояние платежа.
12. Только после всех проверок отметить платеж успешным.
13. Выполнить существующую послеоплатную бизнес-логику.
14. Вернуть FreeKassa именно тот ответ, который требует актуальная документация.

Учесть, что FreeKassa может повторно отправлять уведомление.

Webhook обязан быть идемпотентным.

# 10. HELEKET

Изучи актуальную документацию Heleket.

Для обычной оплаты заказа использовать Invoice flow.

Не использовать Static Wallet для стандартной покупки, если для этого нет отдельной бизнес-причины.

При создании invoice передавать:

* уникальный `order_id`;
* сумму;
* валюту;
* callback URL;
* success URL / return URL, если поддерживается текущим API;
* необходимые параметры согласно документации.

Запросы Heleket должны подписываться строго в соответствии с текущей документацией.

Использовать:

```env
HELEKET_MERCHANT_ID
HELEKET_PAYMENT_API_KEY
```

Не реализовывать алгоритм подписи «примерно».

Проверить:

* порядок сериализации JSON;
* кодирование;
* base64, если требуется;
* HMAC/MD5 — использовать ровно тот алгоритм, который указан в текущей документации.

### Webhook Heleket

Создать:

```text
/api/payments/webhooks/heleket
```

При webhook:

1. Получить исходное тело запроса.
2. Получить signature.
3. Проверить подпись через Payment API Key.
4. Найти invoice по `uuid` / `order_id`.
5. Найти локальный платеж.
6. Проверить сумму.
7. Проверить валюту.
8. Сопоставить внешний статус с внутренним.
9. Только после проверки обновить БД.

Heleket имеет несколько статусов.

Не сводить всё просто к:

```python
if status != "paid":
    failed
```

Сделай нормальный mapping.

Например внутренние состояния:

```text
pending
processing
paid
failed
cancelled
underpaid
overpaid
refunded
```

Но используй существующие enums проекта, если они уже есть.

Особенно правильно обработать состояния типа:

```text
process
check
paid
paid_over
wrong_amount
cancel
fail
system_fail
refund_process
refund_fail
refund_paid
locked
```

Проверь их актуальный список в документации перед реализацией.

`paid_over` нельзя автоматически считать ошибкой только потому, что сумма выше ожидаемой.

Логику обработки переплаты сделать осознанно.

`wrong_amount` также не должен автоматически выдавать заказ как полностью оплаченный.

# 11. CRYSTALPAY

Использовать актуальную версию CrystalPay API.

Перед реализацией проверить официальную документацию v3.

Не брать примеры v2, если существует соответствующий v3 endpoint.

Для создания платежа использовать актуальный invoice endpoint.

Тип инвойса для обычной покупки должен соответствовать покупке с фиксированной суммой.

Не использовать режим произвольного пополнения, если заказ должен стоить строго определённую сумму.

Передавать:

* amount;
* currency;
* description;
* lifetime;
* redirect_url;
* callback_url;
* `extra`.

В `extra` удобно сохранить наш внутренний ID платежа или заказа.

Но не полагаться исключительно на `extra`.

Сохранять полученный CrystalPay invoice ID в БД:

```text
provider_payment_id
```

Сохранять payment URL.

### Callback CrystalPay

Создать:

```text
/api/payments/webhooks/crystalpay
```

Проверять `signature`.

Использовать актуальный `salt` кассы и алгоритм подписи ровно по документации текущей версии API.

Использовать безопасное сравнение хешей:

```python
hmac.compare_digest(...)
```

Нельзя просто доверять полю:

```json
{
    "state": "..."
}
```

без проверки подписи.

После проверки:

* найти invoice;
* найти локальный платеж;
* проверить ID;
* проверить сумму;
* проверить валюту;
* проверить конечный state;
* провести идемпотентное изменение состояния.

Не хардкодить старые значения статусов из v2 без проверки текущей документации v3.

# 12. WEBHOOK — ГЛАВНОЕ ПРАВИЛО

Redirect пользователя после оплаты НЕ означает успешную оплату.

То есть:

```text
/payment/success
```

не должен делать:

```python
order.status = "paid"
```

НИКОГДА.

Success page означает только:

> пользователь вернулся со страницы платежной системы.

Единственный источник истины:

1. валидный подписанный webhook;

или

2. серверная проверка статуса платежа через API провайдера.

---

# 13. ИДЕМПОТЕНТНОСТЬ

Все webhook должны быть идемпотентными.

Платёжная система может отправить один callback несколько раз.

Если:

```python
payment.status == PAID
```

повторный webhook не должен повторно:

* начислять баланс;
* создавать заказ;
* запускать услугу;
* менять деньги;
* начислять бонус;
* отправлять одну и ту же операцию;
* повторно выполнять after-payment hook.

Нужна защита как минимум на уровне БД/транзакции.

Если архитектура позволяет — используй row lock / transactional update / уникальные constraints.

Особенно учти ситуацию:

```text
Webhook A
Webhook B
```

приходят практически одновременно.

Оба не должны одновременно решить, что платеж ещё не обработан.

# 14. ТРАНЗАКЦИОННОСТЬ

Финальное подтверждение платежа должно происходить атомарно.

Условно:

```text
BEGIN

lock payment

проверить status

обновить payment

обновить order

запустить необходимую DB business logic

COMMIT
```

Если внутри существующей архитектуры используется Unit of Work или иной механизм — используй его.

Не оставлять ситуацию:

```text
payment = paid
order = unpaid
```

из-за исключения между двумя update.

Не менять существующие статусы заказов без необходимости.

# 16. ПОВТОРНОЕ СОЗДАНИЕ ПЛАТЕЖА

Продумать сценарий:

Пользователь создал FreeKassa invoice, но не оплатил.

Потом решил выбрать Heleket.

Это допустимо.

У заказа может существовать несколько payment attempts.

Но успешным должен стать только корректный оплаченный платеж.

После успешной оплаты одного payment attempt:

* заказ становится оплаченным;
* остальные неоплаченные attempts не должны каким-либо образом повторно активировать заказ.

Если после оплаты заказа неожиданно приходит успешный webhook от второго провайдера — это отдельная аномальная ситуация.

Не игнорировать её молча.

Записать structured warning/error и не запускать бизнес-логику повторно.

# 19. HTTP CLIENT

Не плодить новый HTTP client для каждого провайдера без необходимости.

Если проект асинхронный — использовать существующий async HTTP подход.

Например общий:

```python
httpx.AsyncClient
```

с:

* timeout;
* обработкой сетевых ошибок;
* проверкой HTTP status;
* контролируемыми retry.

Retry разрешён только там, где это безопасно.

Особенно осторожно с `create_payment`, потому что повтор POST после timeout может создать второй invoice.

Использовать provider idempotency mechanism, если конкретный API его предоставляет.

Если не предоставляет — учитывать это архитектурно.

* secret;
* API key;
* authorization данные;
* полные чувствительные payload, если в них могут присутствовать секретные/персональные данные.

Пример:

```text
payment.created
provider=heleket
order_id=1251
payment_id=918
provider_payment_id=...
```

# 23. БЕЗОПАСНОСТЬ WEBHOOK

Для каждого провайдера выполнить максимально возможную проверку:

* merchant/shop ID;
* provider payment ID;
* internal order ID;
* amount;
* currency;
* допустимый статус;
* состояние локального платежа.

Если официальный провайдер публикует IP webhook серверов, IP allowlist можно использовать как дополнительную защиту, но НЕ вместо проверки криптографической подписи.

Особенно аккуратно работать за reverse proxy.

Нельзя слепо доверять:

```text
X-Forwarded-For
X-Real-IP
```

без настройки trusted proxy.

# 25. ENV VALIDATION

Если провайдер включён, но необходимые environment variables отсутствуют — приложение должно выдавать понятную ошибку конфигурации.

Но отсутствие ключей, например, Heleket не должно обязательно ломать запуск всего проекта, если этот provider отключён.

Можно предусмотреть:

```env
PAYMENTS_FREEKASSA_ENABLED=true
PAYMENTS_HELEKET_ENABLED=true
PAYMENTS_CRYSTALPAY_ENABLED=true
```

только если это соответствует существующему стилю конфигурации.

Не добавлять feature flags без необходимости.

# ГЛАВНЫЙ РЕЗУЛЬТАТ

После выполнения задачи должна существовать одна понятная платежная система:

```text
                         ┌─ YooKassa
                         │
Frontend -> Backend -> PaymentService ─ FreeKassa
                         │
                         ├─ Heleket
                         │
                         └─ CrystalPay
```

При этом:

```text
ORDER
  |
  +-- payment attempt YooKassa
  +-- payment attempt FreeKassa
  +-- payment attempt Heleket
  +-- payment attempt CrystalPay
```

но сам заказ остаётся единым.

Статус `PAID` выставляется только после серверного подтверждения оплаты.

Ни один пользовательский запрос с frontend не должен иметь возможности самостоятельно сделать заказ оплаченным.

Существующая бизнес-логика после оплаты должна выполняться ОДИН раз независимо от того, каким платежным провайдером воспользовался пользователь.

Сначала изучи код проекта целиком в области payments/orders/database/config/frontend checkout, затем приступай к изменениям.
