# Задача: внедрить систему единого аккаунта и привязки способов авторизации

Рабочий проект уже существует.

Рабочая директория:

```text
/home/ava/king
```

Стек проекта:

- Frontend: React + Vite
- Backend: Python
- База данных: PostgreSQL

ВАЖНО:

Не создавай новую систему авторизации с нуля.

Сначала полностью изучи существующий проект, текущую авторизацию, структуру PostgreSQL и существующие интеграции, после чего аккуратно расширь текущую архитектуру.

На данный момент в проекте используются:

- обычная авторизация пользователя через существующую систему логина;
- Telegram — авторизация реализована через Telegram-бота;
- VK — авторизация реализована через VK ID.

Google, Discord, GitHub и другие OAuth-провайдеры сейчас внедрять НЕ НУЖНО.

Также необходимо реализовать возможность привязки email к единому аккаунту.

# 2. Главная концепция

```text

        ↓
```

Основной сущностью всегда остаётся:

```text
user_id
```

# 6. Telegram

Telegram authentication в проекте УЖЕ существует и работает через Telegram-бота.

НЕ создавай новую Telegram OAuth-систему.

Сначала изучи существующую реализацию Telegram-бота.

Необходимо интегрировать её в систему единого аккаунта.

Пользователь, который уже авторизован на сайте, должен иметь возможность:

```text
Аккаунт
→ Telegram
→ Подключить
```

После этого существующая Telegram-механика должна подтвердить Telegram-пользователя.

Полученный Telegram ID необходимо связать именно с:

```text
current_user.id
```

Пример:

```text
user_id = 42
telegram_id = 827361827
```

После этого при следующей авторизации через Telegram backend должен определить:

```text
telegram_id
↓
связанный user_id
↓
User
```

и авторизовать существующего пользователя.

Новый пользователь создаваться не должен, если Telegram уже связан с существующим аккаунтом.

# 8. Критически важно: LOGIN и CONNECT — разные операции

Это принципиальное требование.

Не смешивай два сценария.

## LOGIN

Пользователь НЕ авторизован.

Например нажимает:

```text
Войти через Telegram
```

или:

```text
Войти через VK
```

Backend должен найти связь:

```text
provider
+
provider_user_id
↓
user_id
↓
users
```

и создать обычную авторизованную сессию / JWT существующего пользователя.

---

## CONNECT

Пользователь УЖЕ авторизован.

Открывает:

```text
Аккаунт
→ Способы входа
```

и нажимает:

```text
Подключить Telegram
```

или:

```text
Подключить VK
```

После подтверждения внешний аккаунт должен связаться строго с:

```text
current_user.id
```

Нельзя в этот момент создавать нового User.

# 9. Привязка Email

Необходимо также реализовать возможность привязывать Email к аккаунту.

На данный момент полноценной системы email-рассылки и отправки писем с кодом подтверждения в проекте нет.

Поэтому сейчас необходимо реализовать только архитектуру email verification.

Пользователь должен иметь возможность:

```text
Аккаунт
→ Email
→ Добавить Email
```

После этого email сохраняется в PostgreSQL.

Например:

```text
email = user@example.com
email_verified = false
```

Для новых пользователей / новых добавленных email почта должна считаться:

```text
НЕ подтверждённой
```

до полноценного подтверждения через письмо.

# 11. Старые пользователи с Email

В базе уже существуют пользователи, которые были зарегистрированы раньше и уже имеют Email.

К ним необходимо применить специальное правило миграции.

ВСЕ существующие до внедрения этой системы пользователи, у которых Email уже находится в базе, должны автоматически считаться:

```text
email_verified = true
```

То есть их email считается подтверждённым автоматически.

Не заставляй существующих пользователей подтверждать старый email.

Пример:

До миграции:

```text
id = 25
email = olduser@example.com
```

После миграции:

```text
id = 25
email = olduser@example.com
email_verified = true
```


```text

```



Очень важно:

не использовать просто:


в runtime-коде для определения подтверждённости.

Сделай нормальное поле состояния в базе данных и корректно заполни его миграцией.

# 13. Email должен быть уникальным

Изучи текущие ограничения БД.

Если архитектура проекта предполагает уникальный Email пользователя, сохрани это правило.

Нельзя позволить двум независимым аккаунтам привязать один и тот же Email, если текущая система предполагает уникальность Email.

Backend должен проверять конфликт.

Например:

```text
Этот Email уже используется другим аккаунтом.
```

Не выполняй автоматическое объединение пользователей только на основании одинакового Email.

---

# 14. Нельзя автоматически объединять аккаунты

Это очень важное правило.

Нельзя автоматически решить:

```text
у двух пользователей одинаковый email
→ значит это один пользователь
```

или:

```text
VK вернул такой же email
→ объединить аккаунты
```

или:

```text
Telegram username совпадает
→ объединить аккаунты
```

Объединение должно происходить только через явную операцию:

```text
авторизованный пользователь
→ Аккаунт
→ Подключить Telegram / VK / Email
```

# 16. Ограничение уникальности

Один внешний аккаунт нельзя подключить к двум пользователям.

Необходимо обеспечить на уровне PostgreSQL и backend уникальность примерно такого вида:

```text
UNIQUE(provider, provider_user_id)
```

Например:

```text
telegram + 123456789
```

может принадлежать только одному `user_id`.

Аналогично:

```text
vk + 987654321
```

может принадлежать только одному `user_id`.

# 18. Отключение способов входа

Пользователь должен иметь возможность отключать:

```text
Telegram
VK
```

если после этого у него остаётся хотя бы один рабочий способ авторизации.

Необходимо проверить существующую архитектуру обычного login/password.

Нельзя позволить пользователю удалить последний рабочий способ входа и заблокировать себе аккаунт.

Например:

```text
Нет пароля
+
есть только Telegram
```

и пользователь пытается удалить Telegram.

Backend должен запретить действие.

Сообщение:

```text
Нельзя отключить единственный доступный способ входа.
Сначала подключите другой способ авторизации.
```

Эта проверка должна находиться на backend, а не только frontend.

# 21. Безопасность

Для VK ID используй существующую официальную схему авторизации проекта.

Для Telegram используй существующий механизм Telegram-бота.

Backend должен самостоятельно проверять identity.

Нельзя доверять данным вида:

```text
telegram_id
vk_id
provider_user_id
```

если frontend просто прислал их самостоятельно.

Frontend не должен иметь возможность сделать:

```text
POST
{
    "telegram_id": "чужой_id"
}
```

и тем самым привязать чужой Telegram.

Привязка должна происходить только после реального подтверждения личности через существующий Telegram/VK flow.

---

# 22. Не хранить лишние токены

Если VK ID используется только для входа, не храни лишние access token бессрочно без необходимости.

Храни только данные, которые действительно необходимы для:

```text
внешний аккаунт
↓
user_id
```

Если текущая VK ID реализация требует токены, следуй существующей безопасной архитектуре проекта.

---

# 23. Миграция PostgreSQL

Если используется Alembic, создай полноценную миграцию.

Если используется другая система миграций — используй её.

Не удаляй существующие данные.

Миграция должна:

1. добавить необходимые структуры для связанных аккаунтов;
2. добавить `email_verified`, если аналогичного поля ещё нет;
3. для существующих пользователей с Email установить:

```text
email_verified = true
```

4. для новых записей по умолчанию использовать:

```text
email_verified = false
```

если это новый Email, который требует подтверждения.

Очень важно корректно различить:

```text
старые существующие email
```

и:

```text
email, добавленные после внедрения системы
```

После изменений обязательно должны продолжить работать:

- существующий обычный login;
- logout;
- Telegram login;
- VK ID login;
- JWT;
- refresh token;

# 30. Финальная архитектура

В результате должна получиться структура примерно следующего вида:

```text
                    ┌─ Login / Password
                    │
                    ├─ Telegram
                    │
USER ID ────────────┼─ VK ID
                    │
                    └─ Email
```

Главная сущность:

```text
USER
```

имеет один:

```text
user_id
```

Telegram, VK ID, Email и существующий login являются способами доступа к одному и тому же аккаунту.

Email дополнительно имеет состояние:

```text
verified = true / false
```

Для существующих пользователей:

```text
true
```

Для новых Email:

```text
false
```

до появления полноценной системы подтверждения Email.
