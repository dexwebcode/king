# Задача: полностью переработать структуру и UI OrderCard

Работаем с существующим компонентом оформления заказа `OrderCard`.

Нужно **перестроить структуру интерфейса OrderCard**, но сохранить существующую бизнес-логику:

* получение платформ;
* получение типов услуг;
* получение услуг;
* ограничения услуг;
* минимальное/максимальное количество;
* расчёт стоимости;
* проверку ссылки;
* авторизацию;
* существующую систему оплаты;
* создание платежа;
* API;
* текущие данные backend.

Не переписывай бизнес-логику без необходимости.

Сначала изучи существующий `OrderCard`, его дочерние компоненты, API и структуру данных услуг, а уже затем изменяй интерфейс.

---

# 1. Новая главная структура OrderCard

Полностью отказаться от текущего вытянутого вертикального оформления.

Теперь `OrderCard` должна представлять собой **единый компактный центральный блок**, состоящий из двух колонок:

```text
┌─────────────────────────────────────────────────────────────┐
│                        Быстрый заказ                        │
│                                                             │
│  Левая часть ~ 2/3             Правая часть ~ 1/3          │
│                                                             │
│  Выбор параметров               Итог заказа                 │
│  заказа                         / Summary                   │
│                                                             │
│  Платформа                      Платформа                    │
│  Тип услуги                     Услуга                       │
│  Услуга                         Скорость                     │
│  Количество                     Количество                   │
│  Оплата                         Цена                         │
│                                 Ссылка                       │
│                                 ----------------            │
│                                 Итого                        │
│                                 [ Оплатить ]                 │
└─────────────────────────────────────────────────────────────┘
```

Пропорции:

* левая колонка — примерно `2/3`;
* правая колонка — примерно `1/3`.

Например:

```css
grid-template-columns: minmax(0, 2fr) minmax(280px, 1fr);
```

Но не копируй это буквально, если текущая архитектура требует другого решения.

Главное — визуальная пропорция примерно **66% / 34%**.

---

# 2. OrderCard должна быть компактной

Главная цель новой структуры — избавиться от ощущения огромной вытянутой формы.

Карточка должна находиться примерно по центру экрана и выглядеть компактно.

Не нужно растягивать каждый этап на огромную высоту.

Всё содержимое должно быть собрано плотнее:

* заголовок;
* платформы;
* услуги;
* количество;
* способы оплаты;
* итог заказа.

Использовать нормальные небольшие `gap`, `padding` и размеры элементов.

Не создавать огромные пустые пространства.

---

# 3. Заголовок

В верхней левой части карточки должен находиться заголовок:

**Быстрый заказ**

Он должен быть визуальным началом блока.

Не центрировать его относительно всей страницы.

Он должен начинаться по одной вертикальной линии с содержимым левой колонки.

---

# 4. Правая колонка — «Итог заказа»

Правая часть должна быть отдельной визуальной панелью.

Это постоянный `Order Summary`.

Она должна присутствовать с самого начала оформления заказа.

Изначально панель практически пустая.

Например:

```text
Итог заказа

Пока ничего не выбрано
```

По мере заполнения заказа информация автоматически появляется в этой панели.

---

# 5. Progressive Summary

Правая панель должна динамически обновляться.

Не показывай заранее строки с `—`, если пользователь ещё ничего не выбрал.

Лучше постепенно добавлять параметры.

Например пользователь выбрал платформу:

```text
Итог заказа

Платформа
Telegram
```

Выбрал услугу:

```text
Итог заказа

Платформа
Telegram

Услуга
Просмотры
```

Выбрал конкретный тариф:

```text
Платформа
Telegram

Услуга
Просмотры

Скорость
5000 / сутки

Цена за 1000
149 ₽
```

Выбрал количество:

```text
Платформа
Telegram

Услуга
Просмотры

Количество
5000

Скорость
5000 / сутки

Итого
745 ₽
```

Используй реальные параметры, которые существуют в текущих данных услуги.

Не выдумывай поля.

---

# 6. Платформы на главной странице

На панели **«Быстрый заказ» на главной странице** нужно немного сократить количество отображаемых платформ.

Убрать из быстрого заказа:

* Apple Music;
* Spotify;
* Shazam;
* RuTube.

Не удалять эти платформы из системы и каталога.

Они просто не должны отображаться в компактной панели быстрого заказа.

---

# 7. «Больше соцсетей в каталоге»

В освободившееся место в последней колонке списка платформ добавить отдельный элемент:

**Больше соцсетей в каталоге**

Это должен быть визуально понятный элемент, отличающийся от обычной платформы.

Например:

```text
┌─────────────────────┐
│       +             │
│ Больше соцсетей     │
│    в каталоге       │
└─────────────────────┘
```

При нажатии должен использоваться существующий маршрут каталога услуг/соцсетей.

Не создавай новый каталог, если в проекте он уже существует.

---

# 8. Выбор типа услуги

Сохраняем иконки типов услуг.

Использовать существующие изображения из:

`assets/icons`

Соответствие:

* Лайки → `likes.png`
* Репосты → `repost.png`
* Комментарии → `comments.png`
* Просмотры → `show.png`
* Прослушивания → `listening.png`
* Подписчики → `subscribe.png`
* Сохранения → `save.png`
* Статистика → `stats.png`
* Истории → `history.png`
* Подкасты → `podcasts.png`
* Трансляции → `translation.png`
* Друзья → `friends.png`
* Опросы → `opros.png`

Карточка типа услуги должна быть полностью кликабельной.

Отдельную кнопку `Выбрать` внутри карточек не использовать.

---

# 9. Карточки конкретных услуг

Карточки конкретных услуг необходимо сделать компактнее.

Сейчас в них выводится информация:

* минимальное количество;
* максимальное количество;
* цена;
* другие параметры.

Из самой карточки услуги убрать отображение:

**«Количество от ... до ...»**

или аналогичные надписи с минимальным и максимальным количеством.

Ограничения при этом НЕ удаляются из логики.

Они понадобятся дальше для ползунка количества.

---

# 10. Цена за 1000

Информацию о стоимости конкретной услуги перенести в **правый верхний угол карточки услуги**.

Она должна выглядеть как небольшой овальный badge/pill.

Например:

```text
                ┌──────────────────┐
                │ Цена за 1000     │
                │ 149 ₽            │
                └──────────────────┘
```

Или:

```text
[ Цена за 1000 · 149 ₽ ]
```

Badge должен соответствовать существующей визуальной стилистике проекта.

Не делать его огромным.

---

# 11. Новый выбор количества

После выбора конкретной услуги появляется блок количества.

Здесь нужно полностью переработать существующий интерфейс.

Количество должно задаваться **двумя способами одновременно**:

1. вручную через input;
2. красивым slider/range.

То есть:

```text
Количество

[ 5 000 ]

●━━━━━━━━━━━━━━━━━━━━━━━━○
1 000                  50 000
```

Input и slider должны быть синхронизированы.

Если пользователь изменил input:

→ перемещается slider.

Если пользователь изменил slider:

→ изменяется input.

---

# 12. Slider должен быть универсальным

Нельзя захардкодить:

```text
min = 100
max = 10000
```

для всех услуг.

Необходимо изучить текущие данные услуги.

В существующих услугах уже есть ограничения:

* минимальное количество;
* максимальное количество.

Использовать именно их.

Условно:

```js
slider.min = selectedService.min
slider.max = selectedService.max
```

Используй реальные названия полей из текущей структуры данных.

---

# 13. Step slider

Также изучи, существует ли у услуги параметр шага количества.

Если существует — использовать его.

Если отдельного параметра нет, определить безопасную существующую логику изменения количества.

Не нарушить ограничения API.

Количество через input также должно проходить валидацию:

```text
min <= quantity <= max
```

Нельзя позволять отправить количество за пределами услуги.

---

# 14. Внешний вид slider

Стандартный браузерный `<input type="range">` без оформления оставлять нельзя.

Необходимо стилизовать его под дизайн проекта.

Нужны:

* аккуратная дорожка;
* заполненная часть дорожки;
* красивый thumb;
* плавное движение;
* hover;
* active;
* фирменный accent;
* нормальное отображение в Chrome/Firefox.

Но не добавляй тяжёлую внешнюю библиотеку только ради slider.

Если это можно качественно сделать CSS — сделать CSS.

---

# 15. После выбора количества подсвечиваем поле ссылки

Как только пользователь выбрал корректное количество, его внимание нужно перевести на поле ссылки.

Поле ссылки находится **в правой панели итогов заказа**.

До выбора количества оно выглядит спокойно и второстепенно.

После выбора количества поле ссылки должно визуально активироваться.

Использовать фирменный accent цвет проекта:

* border;
* glow;
* background accent;
* либо комбинацию этих эффектов.

Не делать агрессивную анимацию.

Задача — визуально показать:

**«Следующий шаг — вставьте ссылку»**

---

# 16. Поле ссылки переносим в правую колонку

Поле для ссылки больше не должно быть отдельным огромным этапом слева.

Оно должно находиться непосредственно внутри `Order Summary`.

Пример:

```text
┌────────────────────────────┐
│ Итог заказа                │
│                            │
│ Telegram                   │
│ Просмотры                  │
│ 5000                       │
│                            │
│ Ссылка                     │
│ ┌────────────────────────┐ │
│ │ https://...            │ │
│ └────────────────────────┘ │
│                            │
│ Итого              745 ₽   │
│                            │
│ [       Оплатить       ]   │
└────────────────────────────┘
```

---

# 17. Проверка ссылки

Существующую проверку ссылки сохранить.

Если сейчас ссылка проверяется каким-либо сервисом/API/валидатором, эту логику не удалять.

Необходимо адаптировать её к новому расположению input.

При ошибке проверки показать ошибку около поля ссылки.

---

# 18. После выбора количества появляются способы оплаты

Когда пользователь:

* выбрал платформу;
* выбрал тип;
* выбрал услугу;
* выбрал количество;

левая часть переходит к следующему состоянию.

Там должны появиться **способы оплаты**.

То есть не нужен отдельный огромный экран оплаты.

Вся логика остаётся внутри одной двухколоночной OrderCard.

Пример:

```text
ЛЕВАЯ ЧАСТЬ

Способ оплаты

[ СБП ]
[ Карта ]
[ ... ]
```

Использовать реальные способы оплаты из текущей системы.

Не создавать mock payment methods.

---

# 19. Правая колонка в этот момент уже заполнена

Одновременно справа уже должна отображаться полная информация:

```text
Итог заказа

Платформа
Telegram

Услуга
Просмотры

Тариф
...

Скорость
...

Количество
5000

Цена за 1000
149 ₽

Ссылка
[                  ]

--------------------

Итого
745 ₽

[ Оплатить ]
```

Состав полей должен соответствовать реальным данным заказа.

---

# 20. Логика кнопки «Оплатить»

Кнопка `Оплатить` изначально disabled.

Она становится активной только если выполнены обязательные условия.

Как минимум:

* выбрана платформа;
* выбрана услуга;
* выбрано корректное количество;
* выбран способ оплаты;
* заполнена ссылка;
* ссылка прошла существующую необходимую проверку.

Если какое-либо обязательное поле отсутствует:

кнопка должна оставаться disabled.

---

# 21. Не создавать заказ без ссылки

Это обязательное требование.

Если поле ссылки пустое, создать заказ невозможно.

Необходимо защитить это не только визуальным `disabled`, но и в обработчике создания заказа.

То есть нельзя обойти проверку простым вызовом обработчика.

---

# 22. Оплата

После заполнения ссылки и выполнения всех условий:

кнопка:

**Оплатить**

становится активной.

После её нажатия используется **существующая система формирования оплаты**.

Не переписывать платёжную интеграцию, если это не требуется для нового UI.

Последовательность:

```text
выбор параметров
→ количество
→ способ оплаты
→ ссылка
→ проверка данных
→ кнопка Оплатить
→ существующее создание заказа/платежа
```

---

# 23. Авторизация

Сохранить существующую ранее реализованную логику авторизации при оформлении заказа.

Если пользователь не авторизован, он всё равно должен иметь возможность:

* выбрать платформу;
* выбрать услугу;
* выбрать количество;
* заполнить данные заказа.

Не заставлять его авторизовываться в начале.

Авторизация должна происходить непосредственно перед операцией, где она действительно необходима для создания заказа/оплаты.

После авторизации состояние сформированного заказа не должно теряться.

Если эта логика уже реализована — адаптировать её к новой структуре, а не переписывать заново.

---

# 24. Главная страница и авторизованный пользователь

Учти, что OrderCard используется в разных состояниях интерфейса.

На главной странице блок называется:

**Быстрый заказ**

и должен быть максимально компактным.

После входа/в личном интерфейсе карточка оформления заказа также не должна снова превращаться в длинную форму на весь экран.

Новая двухколоночная структура должна быть базовой структурой оформления заказа.

При этом на главной странице допускается сокращённый список платформ согласно требованиям выше.

---

# 25. Не использовать огромную step-навигацию

Текущая модель, где каждый этап сильно растягивает карточку по вертикали, больше не нужна.

Не нужно делать:

```text
Шаг 1
огромный блок

Шаг 2
огромный блок

Шаг 3
огромный блок
```

Интерфейс должен ощущаться как **один компактный configurator заказа**.

Выбранные параметры постепенно изменяют содержимое этого configurator.

---

# 26. Высота карточки

Не должно быть сильных скачков высоты OrderCard при выборе разных пунктов.

Основной контейнер должен иметь визуально стабильный размер.

Но не ставить огромный `height`, внутри которого половина места пустая.

Использовать:

* разумный `min-height`;
* flex/grid;
* внутренние области;
* при необходимости локальный scroll для длинного списка услуг.

Не использовать scroll всей страницы там, где можно оставить компактный интерфейс.

---

# 27. Центрирование

Новая OrderCard должна аккуратно помещаться примерно в центральной области viewport.

Не прижимать карточку к самому верху.

Не делать её настолько высокой, чтобы нижняя часть постоянно находилась за пределами экрана.

На обычном desktop-разрешении основной интерфейс оформления желательно видеть практически целиком без большого вертикального скролла.

---

# 28. Адаптив

Desktop:

```text
[       2/3 выбор заказа       ][ 1/3 итог ]
```

Tablet:

можно уменьшать пропорции и размеры внутренних элементов.

Mobile:

две колонки должны превращаться в одну:

```text
Выбор заказа

Итог заказа
```

Не допускать:

* горизонтального scroll;
* обрезанного текста;
* наложения элементов;
* выхода price badge;
* поломки slider.

---

# 29. Визуальная иерархия

Интерфейс должен быть компактным, но не перегруженным.

Использовать визуальные уровни:

### Основное

* название;
* выбранный сервис;
* итог;
* CTA.

### Вторичное

* скорость;
* цена за 1000;
* дополнительные характеристики.

Не делать каждый текст одинаково ярким.

---

# 30. Ничего не хардкодить без необходимости

Особенно запрещено хардкодить:

* цены;
* максимальное количество;
* минимальное количество;
* итоговую стоимость;
* скорость;
* способы оплаты;
* параметры услуги.

Брать всё из существующих данных проекта.

---

# 31. Сначала изучи текущую архитектуру

Перед внесением изменений обязательно найди:

1. основной `OrderCard`;
2. компоненты этапов;
3. данные платформ;
4. получение типов услуг;
5. получение конкретных услуг;
6. структуру объекта услуги;
7. поля `min/max quantity`;
8. расчёт стоимости;
9. скорость выполнения;
10. поле ссылки и его validation;
11. способы оплаты;
12. обработчик `Оплатить`;
13. создание заказа;
14. создание платежа;
15. состояние авторизации;
16. сохранение OrderCard при авторизации;
17. маршрутизацию каталога.

После этого менять UI.

# Ожидаемый UX

## Начальное состояние

```text
Быстрый заказ

┌──────────────────────────────────────────────────────────────┐
│ Платформы / выбор                         │ Итог заказа       │
│                                           │                   │
│ [TG] [VK] [YT] [...]                      │ Пока ничего       │
│                                           │ не выбрано        │
└──────────────────────────────────────────────────────────────┘
```

↓

## Выбрана платформа

Справа появляется платформа.

↓

## Выбран тип услуги

Справа появляется тип услуги.

↓

## Выбрана услуга

Справа появляются:

* услуга;
* цена;
* скорость;
* дополнительные реальные параметры.

Слева появляется количество.

↓

## Количество

```text
Количество

[ 5000 ]

●━━━━━━━━━━━━━━━━━━━━○
```

Количество можно менять:

* вручную;
* slider.

↓

## После выбора количества

Поле ссылки справа подсвечивается accent-цветом.

Слева появляются способы оплаты.

↓

## Финальное состояние

```text
┌──────────────────────────────────────────────────────────────┐
│ Способ оплаты                        │ Итог заказа            │
│                                      │                        │
│ [ СБП ] [ Карта ] [...]              │ Telegram               │
│                                      │ Просмотры              │
│                                      │ Количество: 5000       │
│                                      │ Скорость: ...          │
│                                      │ Цена за 1000: ...      │
│                                      │                        │
│                                      │ Ссылка                 │
│                                      │ [ https://... ]        │
│                                      │                        │
│                                      │ Итого: 745 ₽           │
│                                      │                        │
│                                      │ [ Оплатить ]           │
└──────────────────────────────────────────────────────────────┘
```

↓

Если всё заполнено:

**Оплатить** становится активной.

↓

Используется существующая логика оплаты.

# Важные ограничения

Не нужно:

* переписывать backend без необходимости;
* создавать новые таблицы БД;
* делать новую платёжную систему;
* создавать mock-услуги;
* хардкодить ограничения slider;
* дублировать существующие API;
* удалять Apple Music / Spotify / Shazam / RuTube из общей системы;
* ломать каталог;
* ломать авторизацию;
* ломать существующую проверку ссылки;
* создавать полностью отдельный OrderCard для каждого этапа.

Нужно именно **реорганизовать существующий OrderCard в компактный двухколоночный configurator**.

# Критерии готовности

Работа считается законченной, если:

* OrderCard разделена примерно `2/3 + 1/3`;
* слева находится конфигуратор заказа;
* справа постоянно находится `Итог заказа`;
* summary заполняется постепенно;
* OrderCard стала значительно компактнее;
* заголовок `Быстрый заказ` расположен сверху слева;
* Apple Music убран из быстрого заказа;
* Spotify убран из быстрого заказа;
* Shazam убран из быстрого заказа;
* RuTube убран из быстрого заказа;
* они при этом остались доступны в общей системе/каталоге;
* появился элемент `Больше соцсетей в каталоге`;
* иконки типов услуг сохранены;
* отдельные кнопки `Выбрать` не нужны;
* из карточек услуг убраны min/max quantity;
* `Цена за 1000` находится в compact badge справа сверху;
* количество можно менять вручную;
* количество можно менять slider;
* slider и input синхронизированы;
* `min/max` slider берутся из выбранной услуги;
* невозможно установить количество за пределами разрешённого;
* slider стилизован;
* после количества подсвечивается поле ссылки;
* ссылка находится справа внутри summary;
* после количества слева появляются способы оплаты;
* справа показывается полная информация заказа;
* итоговая стоимость пересчитывается автоматически;
* кнопка `Оплатить` disabled до заполнения обязательных данных;
* невозможно создать заказ с пустой ссылкой;
* существующая проверка ссылки работает;
* существующая логика платежа работает;
* состояние заказа не теряется при авторизации;
* интерфейс не скачет по высоте;
* desktop-версия компактна;
* mobile-версия адаптивна;
* горизонтальной прокрутки нет;
* в консоли нет новых ошибок.
