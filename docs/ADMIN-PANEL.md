# Административная панель KingPromotion

Полноценная админ-панель, встроенная в существующий проект. Не создаёт вторую
систему авторизации, заказов, поддержки или базы: используются существующие
таблицы PostgreSQL, JWT-авторизация и бизнес-логика проекта.

## Доступ

- URL: `/admin` (SPA-маршрут, рендерится из общего бандла frontend).
- Роль администратора — существующий механизм проекта: allowlist `ADMIN_USER_IDS`
  в `backend/.env`. **Как назначить администратора:** добавить ID пользователя
  в `ADMIN_USER_IDS` (через запятую) и перезапустить backend.
- Проверка роли выполняется на backend для **каждого** запроса зависимостью
  `get_current_admin` (`backend/admin/dependencies.py`): обычный пользователь
  получает `403 Forbidden` даже при прямом обращении к `/api/admin/*`.
  Скрытие кнопки на frontend — не механизм безопасности.

## Разделы

Dashboard · Заказы · Пользователи · Отзывы · Поддержка · Финансы · Аналитика ·
Наценка · Логи (журнал действий администраторов).

## Backend

```
backend/admin/
  router.py       — эндпоинты /api/admin/* (26 маршрутов)
  service.py      — отправка заказов поставщику, ручные статусы заказов
  repository.py   — параметризованные SQL-запросы (только PostgreSQL-агрегация)
  statistics.py   — периоды, серии, dashboard-сводка
  settings.py     — app_settings: глобальная наценка, окно активности
  audit.py        — журнал действий администраторов
  schemas.py      — Pydantic-валидация
backend/analytics/ — внутренняя аналитика посещений (beacon)
```

### Основные эндпоинты

| Эндпоинт | Назначение |
|---|---|
| `GET /api/admin/dashboard` | карточки главной страницы (SQL-агрегаты) |
| `GET /api/admin/stats/revenue` · `/users` · `/traffic` | серии графиков (день/неделя/месяц/произвольный) |
| `GET /api/admin/finance` | финансовая сводка (оборот, пополнения, возвраты, прибыль, маржа) |
| `GET /api/admin/orders` + `/:id` + `PATCH /:id/status` | заказы: поиск/фильтры/сортировка/пагинация, детали, ручной статус |
| `GET /api/admin/users` + `/:id` + `ban`/`unban` | пользователи, профиль, блокировка |
| `GET /api/admin/reviews` + `DELETE /:id` + `POST /:id/restore` | отзывы с мягким удалением |
| `/api/admin/support/*` | обращения поддержки (существующая система, дополнена аудитом) |
| `GET/PUT /api/admin/settings/markup` · `/settings/active-window` | глобальная наценка, окно активности |
| `GET /api/admin/audit-log` | журнал действий администраторов |
| `POST /api/analytics/track` | публичный beacon посещений |

## Как считается статистика

- Всё считается в PostgreSQL (`COUNT`/`SUM`/`AVG`/`GROUP BY`/`date_trunc`) —
  тысячи строк не выгружаются во frontend.
- Дата заказа: `payment_attempts.processed_at` (время оплаты) либо legacy-строка
  `orders.date` (`TO_TIMESTAMP(..., 'HH24:MI:SS DD.MM.YYYY')`, Europe/Moscow).
- Заказ считается оплаченным: есть попытка `status='processed'` либо
  (legacy) попытки нет и статус не «Ожидает оплаты»/«Оплата отменена».
- Оборот = оплаченные заказы + пополнения баланса. Прибыль = выручка −
  себестоимость; маржа считается только по заказам с известной себестоимостью
  (`orders.supplier_cost`, для legacy-заказов её нет).
- Возвраты — legacy-транзакции `method='admin'` с отрицательной суммой.
- Активный пользователь: `last_seen_at` в пределах окна
  (`app_settings.active_users_window_minutes`, по умолчанию 30). Запись в БД —
  не чаще раза в 5 минут (`LAST_SEEN_UPDATE_INTERVAL_SECONDS`).
- Посещения: события `traffic_events` (pageview на смену маршрута). Хранятся
  только путь и HMAC анонимного visitor-идентификатора; user_id — только для
  авторизованных. IP и персональные данные не сохраняются.
- Дата регистрации legacy-пользователей восстановлена приблизительно по
  первому заказу (миграция `016`, 32 аккаунта); у новых пользователей
  `created_at` заполняется при регистрации.

## Глобальная наценка

- Одно централизованное значение `app_settings.global_markup_percent`
  (начальное — `KINGPROMOTION_MARKUP_PERCENT` из `.env`).
- Формула применяется в одном месте — `backend/services/get_price.py`:
  `public_rate = provider_rate × (1 + markup/100)`.
- Изменение через админку влияет **только на новые цены**: цена уже созданного
  заказа хранится в `orders.amount`/`orders.supplier_cost` и не пересчитывается.

## Ручное изменение статуса заказа

Разрешено только для оплаченных заказов, ещё не созданных у поставщика
(`id_rocket = 0`): статус заказов у поставщика принадлежит фоновой
синхронизации (`sync_due_orders`), и ручное вмешательство в неё запрещено.
Доступные статусы: «Ожидает отправки», «Отменен», «Требует проверки»,
«Отклонен поставщиком». Каждое изменение пишется в журнал администратора.

## Блокировка пользователей

`POST /api/admin/users/{id}/ban` (причина, кто, когда) ставит `users.banned=1`
и инкрементирует `token_version` — все выданные JWT мгновенно умирают.
Проверка бана выполняется в `get_current_user` (все защищённые эндпоинты)
и при входе (логин/Telegram/VK). Разбан — `POST /api/admin/users/{id}/unban`.
Нельзя заблокировать себя или другого администратора.

## Безопасность

- Все admin-эндпоинты — за `get_current_admin` (backend-проверка, 403).
- Все SQL-запросы параметризованы; сортировки — из фиксированных словарей.
- Frontend отображает только публичные поля: пароли/хеши, `users.token`,
  OAuth-токены, `.env` и API-ключи нигде не отдаются. Привязки соцсетей
  показываются без секретов.
- Отзывы и обращения выводятся как текст (React экранирует), XSS исключён.
- Журнал администратора не содержит паролей/токенов/ключей.
- Beacon посещений rate-limit'ируется по IP (`RATE_LIMIT_TRAFFIC_PER_IP`).

## Миграция

`backend/migrations/016_admin_panel.sql` (идемпотентна, применена к рабочей БД):

- `users.created_at`, `last_seen_at`, `ban_reason`, `banned_by`, `banned_at`;
- `reviews.deleted_at`, `deleted_by` (мягкое удаление);
- таблицы `app_settings`, `traffic_events`, `admin_audit_log`;
- индексы под реальные условия выборок.
