## Примечание

Файлы архитектуры будут разбираться, отталкиваясь от главной точки входа — `main.py`.

Сначала рассматривается сам `main.py`, после чего отдельно и по порядку разбираются подключаемые им модули. После рассматриваются остальные части проекта.

> В каждом модуле будет отражена иерархия папок с дальнейшими коментариями по коду.

## main.py

`main.py` является точкой входа и точкой сборки backend-приложения.

В этом файле создаётся и настраивается объект FastAPI-приложения `app`.
К нему подключаются общая конфигурация, middleware и роутеры отдельных модулей.

### Подключенные модули

```
main.py
├── Авторизация
├── Оплата
└── Получение цен
```

### dependencies.py

Файл содержит FastAPI-зависимости, используемые для определения и проверки текущего авторизованного пользователя.

Основная функция `get_current_user()` получает JWT из заголовка `Authorization`, проверяет его, извлекает ID пользователя и запрашивает данные пользователя из базы данных.

Если токен отсутствует, имеет неправильный формат, недействителен, истёк или соответствующий пользователь не найден — запрос завершается с ошибкой `401 Unauthorized`.

### repository.py

Файл отвечает за прямое взаимодействие модуля авторизации с базой данных PostgreSQL.

В нём находятся SQL-запросы для получения пользователя по логину или электронной почте, поиска пользователя по ID и создания нового пользователя.

`repository.py` не содержит бизнес-логику авторизации: он только получает данные из базы или записывает их.

### router.py
Файл является главным роутером модуля авторизации.

В нём создаётся общий `APIRouter` с префиксом `/auth`, к которому подключаются роутеры базовой авторизации, социальных аккаунтов и Telegram.

Сам файл не содержит бизнес-логики и endpoints, а объединяет отдельные роутеры модуля в один общий роутер модуля авторизации, задаёт ему префикс /auth и подключает внутрь три подроутера:
```
/auth
  ├── auth_router
  ├── vkid_router
  └── telegram_router
```

### routers/auth.py

Файл содержит endpoints базовой авторизации пользователя.

Отвечает за вход, регистрацию, получение данных текущего пользователя и выход из аккаунта.

Основная бизнес-логика входа и регистрации передаётся в `service.py`, а проверка авторизованного пользователя выполняется через `dependencies.py`.

### routers/vkid.py

Файл содержит endpoints авторизации через VK ID.

Получает `access_token` от frontend, проверяет его через VK ID API и получает подтверждённые данные пользователя VK.

После проверки ищет связанный аккаунт KingPromotion. Если связь уже существует — пользователь авторизуется. Если нет — создаётся новый пользователь и привязка его VK ID.

После успешной авторизации создаётся JWT KingPromotion.

### routers/telegram.py

Файл содержит endpoints авторизации и привязки аккаунта через Telegram.

Работает с временными Telegram-сессиями, через которые подтверждается Telegram-аккаунт пользователя.

Поддерживает несколько сценариев:
- привязка Telegram к уже авторизованному пользователю;
- вход через уже привязанный Telegram;
- создание нового аккаунта через Telegram;
- привязка Telegram к существующему аккаунту KingPromotion.

После успешного входа или регистрации создаётся JWT KingPromotion.

### schemas.py

Файл содержит Pydantic-схемы входящих данных модуля авторизации.

Схемы определяют структуру данных, которые backend принимает от frontend, выполняют их нормализацию и первичную валидацию до передачи в router и бизнес-логику.

#### Основные схемы

`EmailRequest`
Базовая схема для сценариев, где требуется email. Проверяет формат электронной почты и нормализует значение.

`LoginRequest`
Схема обычного входа пользователя. Принимает:

* `identifier` — логин или email;
* `password` — пароль пользователя.

`RegisterRequest`
Схема регистрации нового пользователя. Принимает email и пароль и выполняет полную проверку нового пароля.

`CheckEmailRequest`
Схема для операций, где требуется только проверка email.

`TelegramStartRequest`
Схема данных для подтверждения Telegram-сессии. Содержит временный token, Telegram ID и username пользователя.

`TelegramCompleteRegisterRequest`
Схема завершения регистрации через Telegram. Принимает Telegram token, новый логин и пароль.

`TelegramLinkExistingRequest`
Схема привязки Telegram к уже существующему аккаунту KingPromotion. Принимает идентификатор пользователя, пароль и Telegram token.

`VkLoginRequest`
Схема входа через VK ID. Принимает `access_token`, полученный frontend от VK ID.

`schemas.py` проверяет только формат и структуру входящих данных.

Файл не проверяет:

* существует ли пользователь;
* правильный ли пароль;
* настоящий ли VK access token;
* существует ли Telegram-сессия;
* привязан ли социальный аккаунт.

Эти проверки выполняются на следующих уровнях приложения.


### security.py
Файл содержит функции, связанные с безопасностью авторизации пользователей.

Основные задачи файла:

хеширование паролей;
создание JWT-токенов после успешной авторизации;
проверка и декодирование JWT-токенов;
извлечение ID пользователя из JWT.

`hash_md5_password()` создаёт MD5-хеш пароля. Сейчас MD5 используется для совместимости со старой базой данных.

`create_access_token()` создаёт JWT-токен пользователя. В токен записывается ID пользователя и время окончания действия токена.

`decode_access_token()` проверяет JWT-токен, извлекает из него ID пользователя и возвращает его. Если токен повреждён, истёк или имеет неправильный формат — возвращается None.

Файл не занимается поиском пользователей в базе данных и не принимает решение о том, может ли пользователь войти в аккаунт. Он предоставляет вспомогательные функции безопасности для других частей модуля авторизации.

### service.py
Файл содержит бизнес-логику базовой авторизации пользователей.

Основные задачи файла:

- поиск пользователя по логину или электронной почте;
- проверка пароля при входе;
- проверка существования пользователя перед регистрацией;
- создание нового пользователя;
- создание JWT после успешного входа или регистрации;
- обработка ситуации, когда пользователь уже существует.

`login_user()` выполняет сценарий входа пользователя. Функция получает логин или email и пароль, находит пользователя через repository.py, сравнивает хеш пароля и при успешной проверке создаёт JWT.

`register_user()` выполняет сценарий регистрации. Функция проверяет, существует ли пользователь, хеширует пароль, создаёт нового пользователя через repository.py и после успешной регистрации создаёт JWT.

`UserAlreadyExistsError` используется для передачи ошибки о существующем пользователе из бизнес-логики в HTTP-слой.

Файл связывает между собой слой работы с базой данных (repository.py) и функции безопасности (security.py), но сам не содержит SQL-запросов.

### social_accounts.py

Файл содержит общий слой работы с привязанными социальными аккаунтами.

Он используется и VK ID, и Telegram-авторизацией. Поэтому файл не относится к
конкретному провайдеру и не содержит HTTP-endpoints или логику создания JWT.

Основные функции:

* `ensure_user_social_accounts_table()` создаёт таблицу связей, если она ещё не существует;
* `upsert_user_social_account()` создаёт или обновляет привязку провайдера к пользователю;
* `get_user_social_accounts()` возвращает список социальных аккаунтов пользователя;
* `get_user_social_account_by_provider_user_id()` находит пользователя по ID у провайдера.

Таблица хранит пользователя KingPromotion, название провайдера, ID пользователя у
провайдера и его username. Ограничения уникальности не позволяют одному внешнему
аккаунту или одному провайдеру быть привязанными к нескольким аккаунтам.

### telegram_sessions.py

Файл отвечает за временные Telegram-сессии авторизации. Такая сессия связывает
действие на сайте и подтверждение в Telegram-боте.

При создании сессии генерируется случайный token. В PostgreSQL сохраняется только
его SHA-256 хеш, поэтому исходный token не хранится в базе данных. Если настроен
`TELEGRAM_BOT_USERNAME`, backend также возвращает ссылку вида `t.me/<bot>?start=<token>`.

Основные функции:

* `ensure_telegram_auth_sessions_table()` создаёт и поддерживает таблицу временных сессий;
* `create_telegram_auth_session()` создаёт ожидающую подтверждения сессию и удаляет истёкшие;
* `get_telegram_auth_session()` получает данные сессии по token без изменения статуса;
* `complete_telegram_auth_session()` записывает Telegram ID и переводит действующую pending-сессию в `authorized`.

Сессия считается подтверждённой только если token найден, её статус равен `pending`
и срок действия ещё не истёк. Проверку дальнейшей авторизации или привязки
пользователя выполняет `routers/telegram.py`.
