# 02 — Сверка неопределённого исхода отправки заказа

## Зачем это нужно

`dispatch_order()` сначала атомарно переводит локальный заказ в состояние
`Отправляется` (`payment_attempts.dispatch_status = 'sending'`), затем вызывает
`action=add` у поставщика и сохраняет внешний `orders.id_rocket`. Между этими
шагами процесс может быть остановлен (рестарт worker, OOM, потеря сети после
того, как поставщик уже принял заказ, но до получения ответа). Внешний ID в этот
момент неизвестен.

API поставщика (Soc-Rocket) **не поддерживает идемпотентный ключ** для
`action=add` и не предоставляет поиска заказа по внешней ссылке: доступны только
`balance`, `add`, `status`, `cancel`, `refill`. Поэтому автоматически определить,
создался ли заказ у поставщика, невозможно, а «слепой» повтор `add` может создать
дубликат и двойное списание supplier-баланса.

Поэтому автоматический повтор запрещён для состояний неопределённого исхода:

- `sending` — заказ застрял после сбоя процесса (обнаруживается, когда
  `dispatch_started_at` старше 5 минут);
- `unknown` — `action=add` ответил неоднозначно (timeout/OSError) в рамках
  работающего процесса.

Оба состояния попадают в админ-очередь
`GET /api/admin/orders/attention` с `attention_kind = "manual_review"` и
`can_resolve = true`, а автоматический durable-обход (`dispatch_pending_orders`)
их не трогает: его кандидаты — только `not_started`, `insufficient_supplier_balance`
и `supplier_unavailable`.

## Процедура оператора

Оператор вручную сверяется с панелью поставщика по ключевым полям локального
заказа (они видны в очереди внимания): `service_id`, `quantity`, `link` и время
создания. Затем выбирает один из двух исходов.

### 1. Заказ у поставщика НЕ создан

Оператор убедился, что в аккаунте поставщика нет заказа с такими
`service_id`/`quantity`/`link` за нужный период.

```http
POST /api/admin/orders/{order_id}/resolve-dispatch
Content-Type: application/json

{"resolution": "not_created"}
```

Backend атомарно возвращает заказ в `Ожидает отправки` (`dispatch_status` →
`not_started`, `dispatch_started_at` очищается) и немедленно запускает повторную
отправку `dispatch_order()`. Ответ содержит итог отправки (`completed`,
`insufficient_supplier_balance` и т.д.).

### 2. Заказ у поставщика создан (известен внешний ID)

Оператор нашёл заказ в панели поставщика и знает его ID.

```http
POST /api/admin/orders/{order_id}/resolve-dispatch
Content-Type: application/json

{"resolution": "record_order", "supplier_order_id": 9001}
```

Backend **не вызывает `add` повторно**. Вместо этого он сверяет указанный ID через
`action=status`: `service`, `quantity` и `link` должны совпасть с локальным
заказом. При совпадении внешний ID фиксируется в `orders.id_rocket`, статус
переводится по статусу поставщика, `dispatch_status` → `completed`. Если поля не
совпали, либо ID уже привязан к другому локальному заказу (уникальный индекс
`uq_orders_id_rocket`), запрос отклоняется с `409`.

## Коды ответов

| Код | Ситуация |
|---|---|
| `200` | Разрешение выполнено; `dispatch_status` — итог (`recorded` или результат `dispatch_order`) |
| `404` | Заказ не найден |
| `409` | Заказ не в состоянии неопределённого исхода / ещё не истёк таймаут `sending` / поля не совпали / ID занят |
| `503` | Поставщик не настроен |

## Границы ответственности

- `resolve-dispatch` — только для `sending` (stale) и `unknown`, только без
  `id_rocket`, только после оплаты (`payment_status = processed`).
- `sending` моложе 5 минут не разрешается: отправка может ещё выполняться.
- `record_order` не создаёт заказ у поставщика и не делает `cancel`/`refill` —
  только фиксирует уже существующий внешний ID.

## Что делать оператору (пошагово, без жаргона)

Когда в Telegram приходит сообщение «Заказ завис в отправке» или в админ-панели
заказ отмечен как «Ручная проверка»:

1. Откройте админ-панель (`/admin`) и найдите заказ в очереди внимания.
2. Нажмите кнопку **«Разрешить ситуацию»**.
3. Запишите из карточки: ссылку получателя, количество и услугу.
4. Зайдите в личный кабинет поставщика (Soc-Rocket) и поищите заказ с той же
   ссылкой, услугой и количеством за последние несколько минут.
5. Теперь решите:

   **А. Заказа у поставщика НЕТ.** Нажмите «Заказ не создан». Система сама
   отправит заказ заново.

   **Б. Заказ у поставщика ЕСТЬ.** Скопируйте его ID из кабинета поставщика,
   вставьте в поле «ID заказа у поставщика» и нажмите «Заказ создан». Система
   проверит, что услуга, количество и ссылка совпадают, и просто привяжет
   внешний ID — повторно заказ создаваться не будет.

6. Если система вернула ошибку «не совпадает ссылка/услуга/количество» — значит,
   вы ввели не тот ID. Перепроверьте ID в кабинете поставщика и повторите.
7. После успешного разрешения заказ уйдёт из очереди «Ручная проверка».

**Главное правило:** никогда не нажимайте «Заказ не создан», если не проверили
кабинет поставщика. Если заказ на самом деле был создан, повторная отправка
создаст дубль и двойное списание.
