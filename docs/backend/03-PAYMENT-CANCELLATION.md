# 03 — Отмена платежа и поздняя оплата после отмены

## Проблема

Раньше `POST /api/payment-attempts/{id}/cancel` менял только локальный статус и
удалял локальную `confirmation_url`, но **не отменял инвойс у провайдера**. Уже
открытая страница оплаты оставалась рабочей. Если провайдер потом сообщал об
оплате, CrystalPAY и Heleket помечали попытку `paid_after_cancel` **без
зачисления** — деньги «зависали» и требовали ручного урегулирования. YooKassa при
этом зачисляла платёж обычным путём, то есть поведение трёх интеграций различалось.

## Итоговое поведение

### 1. Отмена у провайдера (если поддерживается)

| Провайдер | Отмена инвойса | Что делает backend |
|---|---|---|
| **YooKassa** | `Payment.cancel` | При `/cancel` запрашивает статус: `succeeded` → обрабатывает и возвращает `409`; `pending`/`waiting_for_capture` → закрывает платёж у провайдера. |
| **CrystalPAY** | ❌ нет API закрытия инвойса (у инвойсов нет статуса `canceled`, только `lifetime`) | Полагается на короткий `CRYSTALPAY_INVOICE_LIFETIME_MINUTES` (≤ `PAYMENT_TIMEOUT_MINUTES`). |
| **Heleket** | ❌ нет cancel/close в SDK | Полагается на короткий `HELEKET_INVOICE_LIFETIME_MINUTES` (≤ `PAYMENT_TIMEOUT_MINUTES`). |

### 2. Поздняя оплата после отмены → гарантированное зачисление

Если провайдер всё же подтверждает оплату после локальной отмены (состояние
`cancel_requested`/`canceled`), платёж **зачисляется и исполняется обычным путём**,
а не застревает в `paid_after_cancel`:

- пополнение баланса → баланс зачисляется;
- оплата заказа → заказ переводится в `Ожидает отправки` и отправляется поставщику.

Идемпотентность сохраняется через `FOR UPDATE` + `processed_at` и уникальные
ограничения `transaction`/`payment_attempts`. Каждый такой случай логируется с
маркером `LATE_PAYMENT_AFTER_CANCEL` (provider, attempt_id, order/invoice id) — это
точка алертинга/сверки.

Причина такого выбора: деньги уже списаны у клиента, а refund API есть не у всех
провайдеров и не покрывает все сценарии. Зачисление — безопасный для пользователя
и одинаковый для всех провайдеров исход, а отмена у провайдера (п. 1) сужает окно
возникновения таких случаев.

## Таймер оплаты вместо периодической сверки

У CrystalPAY и Heleket нет cancel API, поэтому периодическая сверка каждого
открытого/отменённого счёта для нашего масштаба избыточна. Вместо неё на фронте
показывается таймер, синхронизированный со временем жизни счёта у провайдера.

- Backend возвращает `expires_at` (ISO 8601, UTC) в ответе создания инвойса
  (`/api/payments/crystalpay/create`, `/api/payments/heleket/create`,
  `/api/payments/yookassa/create`) и в `GET /api/payment-attempts/{id}`.
- Источник `expires_at`: если провайдер вернул `expire_at`/`expired_at`/`expires_at`
  — используется он (Heleket отдаёт `expired_at` в unix-секундах, ЮKassa — строку
  ISO 8601); иначе берётся `created_at + PAYMENT_TIMEOUT_MINUTES`.
- `PAYMENT_TIMEOUT_MINUTES` — единая константа для всех трёх провайдеров, а
  `CRYSTALPAY_INVOICE_LIFETIME_MINUTES`/`HELEKET_INVOICE_LIFETIME_MINUTES` ограничены
  сверху этим же значением, поэтому таймер не расходится с реальным сроком жизни счёта.
- Фронт (`PaymentOverlay.jsx`) ведёт обратный отсчёт MM:SS: за 60 секунд подсвечивает
  таймер («Осталась минута»), по истечении автоматически закрывает окно, показывает
  сообщение «Время оплаты истекло…» и очищает сохранённое локальное состояние.
- Если webhook всё же приходит после закрытия формы (клиент успел оплатить) —
  отрабатывает существующая логика `LATE_PAYMENT_AFTER_CANCEL` с зачислением (см.
  выше) и Telegram-алертом администраторам.

Отдельное действие «Свернуть окно» (без вызова `/cancel`) оставляет платёж активным;
«Отменить платёж» — явный вызов `/cancel`. Оба реализованы в `PaymentOverlay.jsx`.

### Что сознательно НЕ делаем

- ❌ периодический обход отменённых/истёкших инвойсов CrystalPAY/Heleket;
- ❌ reconciliation по каждому открытому счёту;
- ❌ состояния `cancel_pending`/`cancel_confirmed` для этих провайдеров.

Достаточно таймера + закрытия формы + обработки webhook, если он всё же придёт.

## Коды ответов `/api/payment-attempts/{id}/cancel`

| Код | Ситуация |
|---|---|
| `200` | Отмена зафиксирована (для YooKassa — также закрыт платёж у провайдера) |
| `404` | Платёж не найден |
| `409` | Платёж уже оплачен/завершён, либо провайдер уже подтвердил оплату |

## Границы ответственности

- `/cancel` — best-effort отмена у провайдера + гарантированный локальный статус
  `cancel_requested`; локальная отмена не откатывает баланс и не делает refund.
- Поздняя оплата всегда зачисляется, чтобы исключить «зависшие» деньги; refund
  остаётся отдельной будущей задачей, если понадобится по бизнес-правилам.
